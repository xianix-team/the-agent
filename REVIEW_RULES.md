# Repository Telemetry Extraction

Produce a single markdown report that lets a new person understand a repository quickly: what it is built with, how it is organised, what standards it follows, and which paths deserve which level of review.

## Ground rules

- **Facts only.** Every statement must come from something you read in the repository (a file, a config, a manifest, a directory listing). Do not guess, infer intent, or fill in missing details with typical conventions.
- **Cite evidence.** After each finding, name the file it came from, e.g. `(package.json)`.
- **Unknown stays unknown.** If something cannot be determined, write `Not found in repository`. Never write "probably", "likely", or "presumably".
- **Read-only.** Do not modify, install, build, or run anything in the target repo. The only file you write is the report.
- **Markdown only.** The sole output is the markdown report. Do not generate config files, scripts, or any other format.
- **Keep it short.** `REPO_TELEMETRY.md` must not exceed **300 lines**; aim for as short as possible. Prefer compact tables and one-line entries, group similar paths into one row, list dependencies by name and version without commentary, and omit prose that restates what a cited file already says. Never drop a required section or sub-category row to save space; shorten the wording instead.
- **No git history.** Do not report commits, authors, branches, or activity. You may use `git ls-files` to list tracked files.

## Step 1: Detect repository shape

Decide whether the repo is a single project or a monorepo, using only evidence:

- Workspace declarations: `workspaces` in `package.json`, `pnpm-workspace.yaml`, `lerna.json`, `nx.json`, `turbo.json`, `rush.json`, Cargo `[workspace]`, `go.work`, Gradle `settings.gradle*` with multiple includes, Maven multi-module `<modules>`, Bazel `WORKSPACE`/`MODULE.bazel`.
- Several independent manifests in separate subdirectories (e.g. `apps/*`, `packages/*`, `services/*`).

If it is a monorepo, list every package/workspace with its path and the evidence that identifies it, then run Steps 2 to 4 **per package** as well as for the repo root (shared tooling). If it is a single project, treat the root as the only package.

## Step 2: Scan

For the root and for each package, collect from the repo's own files:

1. **Folder structure**: top-level directories and one level below.
2. **Manifests and lockfiles**: `package.json`, `pyproject.toml`, `requirements*.txt`, `go.mod`, `Cargo.toml`, `pom.xml`, `build.gradle*`, `*.csproj`, `Gemfile`, `composer.json`, etc.
3. **Libraries and frameworks**: direct dependencies only, grouped runtime vs dev, versions as declared. For monorepos, note internal packages that depend on each other. Also record runtimes and their versions (e.g. from `.tool-versions`, `.nvmrc`, `.python-version`, manifest engine fields).
4. **Testing**: test directories, framework configs, test scripts.
5. **Standards and linters already configured**: ESLint, Prettier, Biome, Stylelint, Ruff, Flake8, Pylint, Black, isort, mypy, golangci-lint, rustfmt, Clippy, RuboCop, Checkstyle, SpotBugs, `.editorconfig`, pre-commit config, commit-lint, `CODEOWNERS`.
6. **Existing contributor docs**: `CLAUDE.md`, `AGENTS.md`, `.cursorrules`, `CONTRIBUTING.md`, `docs/`.

## Step 3: Classify paths into two buckets

Assign every notable path (including paths inside each monorepo package) to exactly one bucket, based on evidence such as directory names, file contents, `.gitignore`, and header comments.

For every bucket, check **each sub-category below** against `git ls-files` and `.gitignore`, and write one row or line per sub-category: either the matching paths with evidence, or `Not found in repository`. Do not silently skip a sub-category. Also note whether a path is tracked or only git-ignored/untracked.

### Ignore
Paths that should not be reviewed or linted (these map to path filters that skip the path):
- **Vendored / third-party code:** `vendor/`, `third_party/`, `node_modules/`, bundled SDKs
- **Committed build output:** `dist/`, `build/`, `out/`, `target/`, `bin/`, `obj/`, `.next/`, `public/assets/`, `publish.zip`
- **Lockfiles:** `package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`, `poetry.lock`, `Cargo.lock`, `go.sum`, `packages.lock.json`, etc.
- **Generated code:** "generated" / "DO NOT EDIT" / `<auto-generated>` headers (search file contents, not just names), `*.generated.*`, `*.g.cs`, `*.designer.cs`, `*.min.js`, `*.pb.go`, GraphQL/OpenAPI codegen output, compiled assets. Only classify an OpenAPI/schema file as generated if the repo says so; otherwise it is an API schema (High scrutiny).
- **Snapshots and data dumps:** test snapshots, database snapshots/backups, seed dumps (e.g. `__snapshots__/`, `*.snap`, `*-backup/`)
- **Git-ignored local artefacts:** secrets, local config, local data folders named in `.gitignore`

### High scrutiny
Paths that get strict checks. Check each sub-category:
- **Authentication and authorisation:** `auth/`, `login`, `session`, `jwt`, `oauth`, `permissions`, roles, tenant context, credential handling, certificates, secret stores
- **Payments and billing:** `payment/`, `billing/`, `checkout/`, `stripe`
- **Infrastructure and CI/CD:** `terraform/`, `infra/`, `k8s/`, `helm/`, `Dockerfile*`, `docker-compose*`, CI workflow files, `ansible/`, cloud templates, deploy scripts
- **Public API surface:** route/controller/handler/endpoint directories (with file counts), OpenAPI/GraphQL schemas, gateway configs, webhook and MCP endpoints
- **Database migrations and schema definitions:** migrations, models, schemas, index definitions, seed data
- **Security configuration:** CORS, security headers, rate limiting, request limits, data protection, encryption key handling
- **Concurrency-sensitive code:** background jobs, workflow/queue/signal handlers, locks, distributed or cache coordination (only where directory/file names or contents show it)
- **Recently modernised directories:** only if the repo itself states it (README/ADR/doc stating a migration or rewrite); never infer from git history.
- **Test coverage of the above:** for each High-scrutiny area, state whether a matching test directory exists (path or `Not found in repository`).

Each High-scrutiny row records: path, reason, evidence, and (where the repo's own files show it) the relevant facts a reviewer needs, e.g. auth scheme in use, whether endpoints carry authorisation attributes, whether input validation exists. Facts only; do not prescribe review rules.

Everything else is "Standard review" and is not listed individually.

## Step 4: Write the report

Save as `REPO_TELEMETRY.md` in the **root of the analysed repository** unless the user specifies another location. Keep sections in this order. The report is consumed by a PR reviewer agent, so it must describe only what exists.

```markdown
# Repository Telemetry: <repo name>

_Generated from repository contents only._

## 1. Overview
What the repository is, from the README/manifest description. Source cited.

## 2. Repository shape
Single project or monorepo, with evidence. For monorepos: table of packages (name, path, language, purpose from its own manifest/README, evidence).

## 3. Technologies
Frameworks, runtimes and versions, with source files. Per package for monorepos.

## 4. Libraries and dependencies
Runtime and dev dependencies, declared versions, source manifest. Per package for monorepos, with internal package dependencies noted.

## 5. Folder structure
Annotated tree (top level plus one level down). Describe each directory only by what its contents show.

## 6. Testing
Test frameworks, locations, commands.

## 7. Standards and tooling
Linters, formatters, type checkers, commit conventions, editor config, with their config files. Check every tool named in Step 2 item 5 and state explicitly which categories (linter, formatter, `.editorconfig`, pre-commit, commit-lint, `CODEOWNERS`) have no config in tracked files, using `Not found in repository` (e.g. "Linter config: Not found in repository"). Say this as a plain fact; do not recommend tools.

## 8. Path classification
### Ignore
One row per sub-category from Step 3 (vendored, build output, lockfiles, generated, snapshots/dumps, git-ignored local artefacts): path(s), tracked or ignored, evidence, or `Not found in repository`.
### High scrutiny
One row per sub-category from Step 3: path, reason, evidence, relevant repo facts, test-coverage location; or `Not found in repository`.
(Group by package for monorepos.)

```

Do **not** add a "Recommended tool set", "Gaps", or any other recommendation/gap section. Tools appear only in section 8, and only if the repo already configures them. Do not suggest tools, fixes, or improvements, and do not list what is missing or undeterminable. Within a section that has no findings, write `Not found in repository`.

## Final check before saving

- [ ] The report is at most 300 lines (check with `wc -l`) and as concise as possible.
- [ ] Every claim has a cited source file.
- [ ] No speculative wording ("probably", "likely", "seems").
- [ ] Monorepo packages each have their own findings, or the repo is stated to be a single project.
- [ ] Section 7 states `Not found in repository` for each linter/formatter/editor-config category with no config.
- [ ] Every sub-category in the two buckets has a row (paths with evidence, or `Not found in repository`).
- [ ] Generated-code check looked at file contents (headers), not only file names.
- [ ] No git history facts included.
- [ ] Only tools already configured in the repo are mentioned; no recommendations, no gaps section, no gitleaks/ast-grep unless the repo already configures them.
- [ ] The only file written is the markdown report; nothing else in the target repo changed.
